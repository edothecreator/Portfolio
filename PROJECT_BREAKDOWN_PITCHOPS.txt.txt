PITCHOPS — CLOUD & DEVOPS BREAKDOWN

PROJECT SUMMARY
---------------
PitchOps is a containerized multi-service application deployed on AWS with a
fully automated CI/CD pipeline. The frontend is a static Next.js export served
via S3 + CloudFront. The backend is a containerized FastAPI app running on EC2
behind Nginx with Let's Encrypt SSL.

The cloud and DevOps work is the core of this project.

Live: https://pitchopsss.xyz
API: https://api.pitchopsss.xyz
Repo: https://github.com/edothecreator/PitchOps

CI/CD PIPELINE
================================================================================

FRONTEND PIPELINE (GitHub Actions)
------------------------------------
File: .github/workflows/deploy.yml
Trigger: push to main branch

Stages:
  1. CHECKOUT      — actions/checkout@v4
  2. NODE SETUP    — actions/setup-node@v4 (Node 18, npm cache)
  3. INSTALL       — npm ci (deterministic, lockfile-strict)
  4. BUILD         — npm run build (Next.js static export → /out)
  5. AWS AUTH      — OIDC token exchange (no static credentials)
  6. S3 SYNC       — aws s3 sync out/ s3://bucket --delete
  7. CF INVALIDATE — aws cloudfront create-invalidation --paths "/*"

Total deploy time: ~2 minutes from git push to live on CDN.

BACKEND PIPELINE (GitHub Actions — pitchops-backend repo)
-----------------------------------------------------------
File: .github/workflows/deploy.yml
Trigger: push to main branch

Stages:
  1. CHECKOUT    — actions/checkout@v4
  2. DOCKER BUILD— docker build -t pitchops-backend:${{ github.sha }}
  3. TRIVY SCAN  — aquasecurity/trivy-action (exits 1 on HIGH/CRITICAL)
  4. SSH DEPLOY  — appleboy/ssh-action → EC2
                   git pull origin main
                   docker compose down
                   docker compose up -d --build
                   docker system prune -f

Total deploy time: ~3 minutes. Pipeline blocked if Trivy finds CVEs.

================================================================================
AWS AUTHENTICATION — OIDC FEDERATION
================================================================================

WHY OIDC INSTEAD OF IAM USER KEYS?
------------------------------------
IAM user keys are long-lived static credentials. If they leak (git history,
logs, env vars) they're compromised until manually rotated.

OIDC federation works differently:
  1. GitHub's OIDC provider is registered in AWS IAM
  2. At runtime, GitHub Actions requests a short-lived JWT from GitHub
  3. AWS STS validates the JWT against the OIDC provider
  4. AWS returns temporary credentials valid for 15 minutes
  5. Credentials auto-expire — nothing to rotate, nothing to leak

SETUP STEPS COMPLETED:
  1. IAM → Identity Providers → Add Provider
     Type: OpenID Connect
     URL: https://token.actions.githubusercontent.com
     Audience: sts.amazonaws.com

  2. IAM → Roles → Create Role
     Trusted entity: Web identity
     Provider: token.actions.githubusercontent.com
     Trust policy: scoped to edothecreator/PitchOps repo only

  3. GitHub secret: AWS_ROLE_ARN only (no key/secret pair)

GITHUB'S BREAKING CHANGE (July 15, 2026):
-------------------------------------------
GitHub changed the OIDC subject claim format for all new repositories created
after July 15, 2026. Old format:
  repo:edothecreator/PitchOps:ref:refs/heads/main

New immutable-ID format:
  repo:edothecreator@159837701/PitchOps@1386571582:ref:refs/heads/main

Standard trust policies using "repo:org/repo:*" silently fail for new repos.
Fix: trust policy StringLike condition must include BOTH formats.

FINAL TRUST POLICY:
  "StringLike": {
    "token.actions.githubusercontent.com:sub": [
      "repo:edothecreator/*",
      "repo:edothecreator@159837701/*",
      "repo:edothecreator@159837701/PitchOps@1386571582:*"
    ]
  }

Org ID:  159837701  (gh api /users/edothecreator → .id)
Repo ID: 1386571582 (gh api /repos/edothecreator/PitchOps → .id)

IAM ROLE PERMISSIONS (least privilege):
  - s3:PutObject, s3:DeleteObject, s3:ListBucket on the specific bucket
  - cloudfront:CreateInvalidation on the specific distribution
  Nothing else. Role cannot read other S3 buckets, cannot touch EC2, etc.

================================================================================
EC2 — SERVER ARCHITECTURE
================================================================================

LAYERS ON THE EC2 INSTANCE:
  Internet
    → Nginx (host, :443)        — SSL termination, reverse proxy
      → Docker: FastAPI (:8000) — application logic, API proxy
        → Docker: PostgreSQL (:5432) — data persistence

NGINX CONFIGURATION:
  Two server blocks:
    1. :80  → 301 redirect to HTTPS
    2. :443 → SSL (Let's Encrypt) → proxy_pass http://localhost:8000

  SSL handled by Certbot:
    sudo certbot --nginx -d api.pitchopsss.xyz
    Auto-renewal configured via systemd timer

  Why Nginx in front of FastAPI?
    - SSL termination at the edge (FastAPI never handles TLS)
    - Standard pattern — easier cert renewal and rotation
    - FastAPI not directly internet-facing

DOCKER COMPOSE SETUP:
  Two containers:
    pitchops_api      — FastAPI/Uvicorn, port 8000
    pitchops_postgres — PostgreSQL 16, port 5432

  Environment variables (never hardcoded):
    FOOTBALL_API_KEY   — API-Football key (only used server-side)
    FRONTEND_ORIGIN    — CORS allowed origins
    DB_HOST/PORT/NAME  — database connection
    DB_USER/PASSWORD   — database credentials

CONTAINER DEPLOYMENT FLOW:
  GitHub push → Actions SSH into EC2 → git pull → docker compose up --build
  Old containers replaced, new image built fresh from updated code.
  docker system prune -f cleans up old images to save disk space.

SSL/TLS STACK
================================================================================

FRONTEND SSL (AWS ACM + CloudFront):
  - Free AWS-managed certificate
  - Provisioned in us-east-1 (required for CloudFront)
  - DNS validation via CNAME records
  - Auto-renews before expiry
  - Attached to CloudFront distribution as custom SSL cert

BACKEND SSL (Let's Encrypt + Certbot + Nginx):
  - Free 90-day certificate
  - Issued via ACME HTTP-01 challenge (required port 80 open in SG)
  - Certbot writes Nginx SSL config automatically
  - Auto-renewal via systemd timer (certbot.timer)
  - Command used: sudo certbot --nginx -d api.pitchopsss.xyz

MIXED CONTENT ISSUE (solved):
  CloudFront serves HTTPS. If the backend was HTTP, browsers block all API
  calls with "Mixed Content" error. Both endpoints must be HTTPS.
  Solution: Nginx + Let's Encrypt on EC2.

================================================================================
SECURITY DESIGN
================================================================================

NO LONG-LIVED CREDENTIALS IN CI/CD:
  OIDC federation replaces IAM user access keys.
  Only secret stored in GitHub: AWS_ROLE_ARN (not a credential).

API KEY NEVER EXPOSED TO BROWSER:
  API-Football key stored as Docker env var on EC2.
  Frontend calls /standings → EC2 backend → API-Football.
  Browser never sees the key.

IAM LEAST PRIVILEGE:
  CI/CD role can only:
    - Write/delete/list one specific S3 bucket
    - Invalidate one specific CloudFront distribution
  Cannot touch EC2, RDS, other services, other buckets.

CORS LOCKED DOWN:
  FastAPI CORS middleware allows only:
    https://pitchopsss.xyz
    https://www.pitchopsss.xyz
  Rejects requests from any other origin.

CONTAINER ISOLATION:
  FastAPI not directly internet-accessible.
  All traffic goes through Nginx first.
  PostgreSQL not exposed to internet (internal Docker network only).

TRIVY SECURITY SCANNING:
  Every backend Docker build scanned before deploy.
  Pipeline exits code 1 if HIGH or CRITICAL CVEs found.
  Deploy never happens with a vulnerable image.

WHAT MAKES THIS INTERESTING FROM A DEVOPS PERSPECTIVE
================================================================================

1. OIDC FEDERATION
   Most tutorials use IAM user keys. OIDC is the correct production approach.
   Had to debug GitHub's breaking change to immutable subject claims (July 2026).

2. STATIC FRONTEND ON CDN
   Next.js output: 'export' produces pure static files.
   No Node.js server, no container, no scaling concerns.
   S3 + CloudFront handles any traffic at near-zero cost.

3. HTTPS END TO END
   Two different SSL solutions for two different contexts:
   ACM (managed, free, auto-renews) for CloudFront.
   Let's Encrypt (open source, Certbot) for EC2.

4. ZERO-DOWNTIME DEPLOYS
   Frontend: S3 sync + CloudFront invalidation. Old files replaced atomically.
   Backend: docker compose up --build replaces containers in place.

5. SECURITY SCANNING IN PIPELINE
   Trivy blocks deploys with known CVEs. Not just a badge — actually enforced.

6. FULL SEPARATION OF CONCERNS
   Frontend has no knowledge of the data API key.
   Backend proxies all external calls.
   CDN and compute are completely independent.
